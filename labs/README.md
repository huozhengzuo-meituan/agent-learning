# 六组 TypeScript 实验

这些实验验证 Agent 的执行机制。`demo.ts` 使用确定性的脚本替身，不是一个真实 LLM Agent，也不能证明模型质量。真实模型调用见第 0003 课；接入提供商后，需保留协议原始事件、工具调用 ID 和用量信息，再单独评估。

需要 Node.js 22.18+，本次在 Node.js 26.9.0 验证。无 npm 依赖，不必运行 install；Node 原生类型擦除不做类型检查，参见 [Node 官方文档](https://nodejs.org/api/typescript.html)。

每次先读题，给出预期，再运行；卡住先看失败信息，最后才读 `src/reference.ts`。题目给定接口是教学接口，不是任何供应商的标准。每题建议 30–60 分钟；循环可用 90 分钟。

## Lab 01 · 不可信输入到可信契约（0005、0007、0008）

实现 `parseSearchArgs(raw)`：输入必须是普通对象形状，只接受 query 和 limit；query 去首尾空白后长 1–100，limit 缺省 3，只接受 1–5 的整数。禁止模型自行提供 tenantId。

1. 先手写合法、空串、字符串数字、越界和夹带身份五类输入。
2. 实现运行时校验，返回规范化对象；为失败抛出清楚的错误。
3. 通过 Lab01 后额外加一个你认为被遗漏的边界样本。

验收：合法输入被规范化，非法输入在工具执行前失败。参考解要点：`unknown` → 对象形状检查 → 字段白名单 → 各字段校验；TypeScript 类型断言不能代替这条链。思考：模型为什么不应决定当前登录用户？

## Lab 02 · 受约束的执行循环（0009–0012）

实现 `runAgent`，模型适配器每次返回“最终答案”或“一个工具请求”。程序校验决定，执行白名单工具，将结果加入下一轮输入；最多运行 maxSteps 轮，最多尝试 maxToolCalls 次工具调用。

1. 先画出 `user → decision → result → decision` 的正常轨迹。
2. 补完循环，区分 final、step_limit、tool_limit；只有 final 才有最终文本。
3. 未知工具反馈 unknown_tool；工具异常反馈 tool_failed，不暴露堆栈；非法模型结构直接失败。
4. 在调用前和 await 后检查取消信号，不允许模型返回后已取消的请求再启动工具。
5. 用 tests 中的“永远调用工具”替身验证停止条件。

验收：正常返回有两次模型调用、一次工具执行；无限请求被限制；`constructor` 不能被当作原型工具调用；取消不会启动下一项副作用。

参考解要点：停止策略属于程序；真实工具结果必须进入下一次模型输入。简化边界：一次只执行一个工具，不包含实际 token/cost 预算、并行调用、provider 消息序列转换或硬超时。AbortSignal 只有被下游正确消费才可中断等待；若适配器永不返回，步数限制不能结束它。扩展题：为模型和工具分别设置期限，验证超时返回后也不会启动写操作。

## Lab 03 · 带权限的检索基线（0013、0015–0017）

实现 `retrieve`：以空白分隔查询词、去重、转小写；按匹配词数量降序，同分按文档 id 排序；只返回当前 tenant 的文档，最多 k 条，无匹配返回空。

1. 先预测三个 demo 文档的排名。
2. 故意把租户过滤放到 top-k 后，找出它会漏掉正确结果的例子。
3. 修正过滤顺序，检验无命中时不拿无关材料填满 k。

验收：从不返回其他租户文档；排序稳定。参考解要点：授权过滤先于排名和截断。此算法只是简单关键词子串基线，不是中文分词、BM25 或向量检索。迁移：换 embedding 检索后，保留同样的权限约束和评估集。

## Lab 04 · 批准与幂等（0021、0022、0028）

实现 `executeApprovedWrite`：依据服务器保存的操作 id 查询固定的 title、actorId、tenantId 和 approved；核对身份与批准后创建收据，重复同一操作返回原收据。

1. 建立已批准和未批准操作。
2. 同一用户重复执行；再更换用户或租户重放相同 id。
3. 修改返回对象，验证不会间接修改服务器收据。

验收：未批准不写入；跨用户/租户重放失败；同一授权操作只有一个逻辑收据。参考解要点：身份来自服务端，执行内容来自批准时保存的动作。Map 只是单进程同步示范，不含真正工单系统；生产需要不可变动作摘要、批准失效/撤销、事务唯一约束及下游幂等键，不能把本题当分布式 exactly-once 保证。

## Lab 05 · 不被旧事件污染的 UI（0019、0020）

实现 `reduceUI`：只消费当前 runId 的下一条有序事件；重复事件忽略；跳号报错以触发重新同步；done/cancelled/failed 都是终态，后续事件不能复活任务。

1. 输入旧 runId 的 delta。
2. 重放同一 sequence；再跳过一条 delta。
3. cancel 后继续发送 done 和 delta。

验收：文本不重复，旧任务不污染新任务，取消保持终态，丢包可见。参考解要点：同时处理运行身份、事件序号和状态边界。此 reducer 假设有序流；服务端取消、持久事件回放和缺口恢复需要额外实现。UI 显示取消不等于服务端动作已停止。

## Lab 06 · 将“看起来成功”变成明确检查（0023–0026）

实现 `grade`：检查最终状态、必需证据 id 和禁止使用的工具。输出所有失败理由，而不是只返回第一项。

1. 构造“答案说已完成但任务达到步数上限”的实际结果。
2. 构造“有引用但调用了禁止工具”的结果。
3. 构造三项结构检查都通过、正文却胡说的结果。

验收：前两类失败可见；能解释第三类为什么需要另外的语义/证据支持性评审。参考实现只证明可验证约束，不能证明回答事实正确。`data/eval-cases.jsonl` 提供综合项目的 30 条人工设计任务种子，需接入真实执行结果和评分器后才能产出模型评估报告。
