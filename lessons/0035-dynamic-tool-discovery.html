工具发现与代码执行式工具组合

按任务发现少量相关工具，并在受控执行环境中聚合数据后返回模型。

阅读 10–15 分钟 · 练习 20–40 分钟来源核对：2026-09-22应用侧 · TypeScript

本课交付：按任务发现少量相关工具，并在受控执行环境中聚合数据后返回模型。

前置：0007 为模型设计清晰的工具契约、0014 选择下一步真正需要的上下文、0028 工具权限与执行隔离、0029 MCP 连接了什么，留下了什么、0034 Skills 与渐进式上下文加载

场景统一使用虚构文档与工单。代码注明示意时，需要接入你自己的项目上下文；本页不会发起模型调用。

先理解这个工程问题

工具库变大时，每次携带全部 schema 会占用上下文并增加选择负担。工具发现先让模型或路由器检索能力描述，再加载少量精确契约。发现结果只是候选，不能越过租户权限或启用未审核的服务器。还需要测试“该找的工具找不到”和“名字相近却选错工具”的情况。

Anthropic 的高级工具使用文章介绍按需发现与程序化调用方向；发布时部分能力为 beta，当前可用性应查目标平台文档，不把历史状态当成永久状态。代码执行结合 MCP 的文章展示另一种思路：先在执行环境处理大量结果，再只把需要的摘要交给模型。

例如统计 500 个工单中的高优先级数量，不必让模型读完全部正文。代码调用受控工具、过滤并聚合，返回计数、采样证据 ID 与是否截断。保留审计轨迹能使结果可复核。程序执行不自动保证事实正确，字段语义、分页与时间范围仍要验证。

具体失败场景：工具只返回前 100 个工单，程序把其中 12 个高优先级计为“全量 12 个”。这是分页覆盖错误，节省 token 不能掩盖它。下面代码要求调用方提供完整性标志，结果不完整时拒绝输出全量结论；工具网关和沙箱负责实际权限与隔离。

读一段代码或执行轨迹

先预测输出或指出边界，再对照注释。以下为课程教学片段；基础机制的可运行实验见 实验说明。本课特定集成需按练习自行实现，未声称已运行。

type Ticket = { id: string; priority: "high" | "normal" };
function summarize(rows: Ticket[], complete: boolean) {
  const high = rows.filter(row => row.priority === "high");
  return {
    highPriorityCount: high.length,
    scannedCount: rows.length,
    scope: complete ? "complete" : "partial",
    evidenceIds: high.slice(0, 3).map(row => row.id)
  };
}
console.log(summarize([
  { id: "T-1", priority: "high" },
  { id: "T-2", priority: "normal" }
], false)); // 必须呈现 partial，不能声称扫描了所有工单

动手：把判断变成证据

  1. 为六个虚构工具写短描述，混入 readTicket 与 deleteTicket 两个名称相近的工具；只读任务应仅发现可读候选。
  2. 用固定工单数组实现聚合，分别输入完整分页与缺页数据，保留证据 ID。
  3. 比较“把全文给模型”与“先聚合再给模型”的输入体积；同时记录发现失败与聚合覆盖错误。

验收：未授权工具不进入可执行集合；缺页结果显式标记 partial；性能比较附带质量与覆盖指标。

完成后再展开：参考解与检查思路

先从服务端授权集合中发现工具，再加载 schema。分页程序必须收集到无下一页或达到预算；达到预算时返回覆盖范围和未扫描说明。统计不需要工单正文，因此可以只请求 id/priority，减少数据暴露与传输。

检索练习：不看上文作答

工具只返回部分数据，聚合结果应当如何标记？

答案与原因（离线、无脚本也可阅读）

答案：标为部分结果。局部统计可以有用，但必须保持覆盖边界，不能让模型误读为全量结论。

换个场景再判断

代码执行返回一个数字却没有来源，如何让结果可审计又不把全部数据塞回上下文？

迁移题参考答案

返回查询范围、数据版本、扫描量、截断标志及可追溯的产物 ID；完整中间结果保存在有权限控制的产物存储，模型按需读取证据。避免只保存无法重现的口头结论。
