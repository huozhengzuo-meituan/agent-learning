完成研发知识助手综合项目

把课程能力整合成一个有演示、故障证据和评分报告的研发知识助手。

阅读 10–15 分钟 · 练习 20–40 分钟（综合项目另计）来源核对：2026-09-22应用侧 · TypeScript

本课交付：把课程能力整合成一个有演示、故障证据和评分报告的研发知识助手。

前置：0017 让回答与检索证据对应、0021 把人工确认做成程序约束、0024 评分器、重复试验与回归判断、0025 用执行轨迹定位问题、0033 通过故障注入检验系统边界、0037 后台 Agent 与持久任务生命周期、0038 把实验变成可运行的服务

场景统一使用虚构文档与工单。代码注明示意时，需要接入你自己的项目上下文；本页不会发起模型调用。

先理解这个工程问题

综合项目服务一个明确用户：研发同学输入“根据虚构组件库的发布文档，解释 T-42 的兼容问题，给出有来源的处理建议并准备演示工单创建草稿”。系统先检索证据，再决定是否补查；证据不足时明确缺口；创建演示工单前展示草稿内容并等待批准。项目只使用课程虚构资料，不接真实工单写入。

交付与任务书统一分为四段：A 完成只读 Agent，包含真实模型、工具循环、预算和引用；B 加入前端交互、批准与幂等写入；C 加入恢复、长任务和一种能力扩展；D 完成评估、故障演练与作品交付。每段交付都可演示，完整任务规范与评分表见 CAPSTONE.md，起步练习见 labs。

与任务书统一的验收权重为：任务完成与证据质量 25 分、执行可靠性 20 分、权限与信任边界 20 分、可观测与评估 20 分、产品体验与工程表达 15 分。建议至少 80 分，且未经批准的副作用、跨租户泄露、密钥外露等关键边界样本全部通过。这是教学阈值，不能证明生产系统不存在其他风险。

按 evals 实践同时查看轨迹与最终状态；按 harness 工程案例为执行者提供可查的规格与反馈。具体失败场景是演示一次成功后宣称系统稳定：你还需要普通、证据缺失、过期、注入、取消和恢复等任务类别，以及真实模型测试的明确覆盖范围。

动手：把判断变成证据

  1. 完成四段交付，每段保存一条成功轨迹和一条失败轨迹；将未接入真实模型的部分标记为离线验证。
  2. 先按任务书完成至少两个租户、真实模型适配、30 条种子评估与能力扩展，再准备 6 分钟演示：1 分钟问题与边界、2 分钟成功任务、2 分钟注入或恢复故障、1 分钟指标与限制。
  3. 用评分表自评后，请另一位开发者仅根据 README 复现；记录他遇到的第一处障碍并修复。

验收：可展示有证据回答、拒绝越权、工单创建批准和恢复去重；评分报告包含任务数、配置、失败样例、费用来源与未验证项。

完成后再展开：参考解与检查思路

最小完整作品可以保留单 Agent 与两个只读工具，不必为了复杂而加入多 Agent。展示一条参数被审批绑定的演示工单创建；故障演示用写后超时证明只有一个 issueId。若只跑过夹具，诚实报告工程边界通过，真实模型任务成功率尚未测量，任务书的真实调用要求尚未完成。
