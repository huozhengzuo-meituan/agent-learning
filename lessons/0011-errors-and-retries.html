04 · 执行控制 · LESSON 0011

区分失败类型，再决定是否重试

按失败原因、重复执行风险和剩余预算，决定重试、修复输入或直接停止。

阅读与检查 15–20 分钟动手任务 35 分钟资料核对 2026-09-22

这一课的具体成果

写出一张失败处理表，并验证不能把所有异常都放进同一个无限重试循环。

前置知识：完成第 0010 课，理解尝试次数与逻辑步骤的区别。

失败不只有一种修复方式

网络瞬时故障可能稍后成功；缺少 API Key 需要修配置；输入不符合 schema 需要修参数；文档没有提供相关信息需要补证据。这些失败如果全部“原样再试”，只会浪费预算。先把外部错误归一化为应用能理解的类别，再做恢复决策。

还要分清业务上的无结果与技术异常。搜索返回空列表可以是正常结果，不等于网络请求失败；工具抛出权限错误也不应被包装成“没有相关文档”。对于模型来说，两者代表不同的观察，影响下一步动作。错误类别设计得清楚，重试策略就不需要依靠猜测错误文案。

重试前先问能否安全重复

读一份文档通常可以重复，但提交工单、发消息和扣款可能产生重复副作用。请求超时只说明没有及时收到结果，不证明对端没有执行。如果不清楚动作是否生效，应先核对状态，或通过幂等机制恢复；第 0022 课会专门展开。

本课只对标记为可安全重试的读取动作给出建议。延迟采用递增等待，并留有次数与总截止时间。真实服务遇到限流时还应遵守服务端的 Retry-After 等明确约定，而不是所有错误都固定一秒再次冲击同一接口。

避免两层重试相乘

你的循环重试三次，SDK 内部又重试两次，最终网络尝试数可能远多于你以为的三次。AI SDK settings提供 maxRetries 配置；当前错误处理文档还区分调用开始阶段与流开始后的错误恢复。接入时明确由哪一层控制，并记录实际尝试次数。

流式场景尤其要核对恢复会不会重放先前工具、重复提交片段或保留旧结果。当前文档给出了 streamRetries 的专门语义，但不同锁定版本可能不同。本课不把它简化成“流断了就重跑整个 Agent”，而是先保留逻辑步骤、网络尝试和工具副作用的边界。

把过程放进 TypeScript

自定义错误归一化后的重试判定片段。它只输出等待建议，不发起网络请求；真实响应的错误码需要在适配器层转换。

type Failure = {
  kind: "transient" | "rate-limit" | "auth" | "invalid-input" | "cancelled";
  safeToRepeat: boolean;
  retryAfterMs?: number;
};

function retryDelay(
  failure: Failure,
  attemptsMade: number,
  remainingMs: number,
): number | null {
  if (!failure.safeToRepeat || attemptsMade >= 3) return null;
  if (failure.kind !== "transient" && failure.kind !== "rate-limit") {
    return null;
  }
  const delay = failure.retryAfterMs ??
    Math.min(500 * 2 ** Math.max(0, attemptsMade - 1), 4_000);
  if (!Number.isFinite(delay) || delay < 0) return null;
  // 留出下一次请求的最低时间预算。
  return delay + 1_000 <= remainingMs ? delay : null;
}

返回 null 表示当前策略不重试，调用者还应保留具体原因。这个教学片段没有加入随机抖动，也没有执行真实等待；生产并发流量需要进一步处理抖动、取消和准确的请求预算。

动手：给失败选择恢复方式

  1. 为五个场景填写“重试 / 修复配置 / 修改输入 / 补资料 / 停止”：读取接口 503、凭据缺失、docId 是数字、文档无说明、用户取消。
  2. 用 retryDelay 检查：已尝试两次、还剩 3 秒、transient 且安全重复；再把 safeToRepeat 改成 false。
  3. 补一条有写副作用的超时场景，说明为什么不能用同样规则直接重试。
验收条件

不会重试用户取消；配置和输入错误有明确修复路径；尝试次数与时间上限都生效；超时与未执行没有混为一谈。

做过以后，再看参考答案

503 在安全可重复且预算足够时可重试；凭据缺失修配置；数字 docId 修输入；文档无说明补资料或承认未知；用户取消停止。两次尝试后的建议延迟为 1,000 ms，剩余 3 秒可容纳题目规定的最低下一次预算。safeToRepeat=false 时不重试。写操作超时应先核验状态或使用幂等标识。

停下来，从记忆里回答

写入工单的请求超时了，能直接得出哪个结论？

答案与理由

应选“结果暂不确定”。需要根据业务接口查询状态或使用幂等恢复，而不是仅凭超时重复副作用。

换个需求，还能用吗？

模型连续返回 schema 错误，你会怎样区分“应该修 prompt”与“应该换接口配置”？

迁移题参考要点

先查看错误是否来自不支持的 schema 或模型能力，若是配置问题应修接口；若接口支持但生成内容违反业务规格，再检查输入与提示、给清晰反馈或改字段设计。重复相同失败之前，应有新的可验证假设，且受限于次数预算。
