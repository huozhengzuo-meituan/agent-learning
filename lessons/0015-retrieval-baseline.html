先建立一个能测量的检索基线

对同一组问题测量检索命中，并让 Agent 按证据缺口决定是否继续搜索。

阅读与判断 15–20 分钟实验 20–40 分钟资料核对：2026-09-22

前置：第 0014 课；工具输入输出和预算限制。

能力状态：通用工程机制；本文 TypeScript 是概念示意，未连接真实模型或生产存储。

本课服务于研发知识助手项目；页面备齐不代表已经掌握。以动手结果、解释和后续迁移作为学习证据。

检索是 Agent 的观察工具

“固定取 top-5 再回答”只能作为比较起点。研发问题可能先需要找到模块名称，再根据错误码检索，再打开具体版本的原文。现代 Agent 可以根据上一轮结果改变查询和读取对象。LangChain 当前检索文档同时讨论固定两步、Agent 自主检索和混合方法，差异在于谁决定检索时机与次数。资料：Retrieval。

本课先做一个可解释的词项命中基线，是为了判断后续向量、重排和自主搜索是否真的改善了结果。它不是最终架构，也不是中文通用搜索算法。把每个查询和文档事先写成词项数组，可以暂时避开分词实现，专注理解测量。

type Doc = { id: string; terms: string[] };
function retrieve(query: string[], docs: Doc[], k: number): string[] {
  const wanted = new Set(query);
  return docs.map(doc => ({ id: doc.id,
    score: [...new Set(doc.terms)].filter(t => wanted.has(t)).length
  })).filter(x => x.score > 0)
    .sort((a, b) => b.score - a.score || a.id.localeCompare(b.id))
    .slice(0, k).map(x => x.id);
}
function recallAtK(found: string[], relevant: string[]): number | null {
  if (relevant.length === 0) return null;
  const hits = new Set(found);
  return new Set(relevant.filter(id => hits.has(id))).size /
    new Set(relevant).size;
}

把“继续搜索”变成有依据的决定

给模型 search(query) 和 read(id) 两个工具。search 返回标题、短摘要、更新时间与授权内的 ID；read 返回原文片段和版本。模型可以自主选词，但执行器限制最大查询次数和返回大小。权限过滤在结果交给模型之前完成，不能把其他租户的命中交给模型自行忽略。

  1. 查询症状
    “构建失败”
  2. 读候选文档
    找到错误码 E42
  3. 改写检索
    “E42 项目版本”
  4. 核对证据
    回答或说明不足

每一步记录 query、候选、真正读取的文档和停止原因。不能用“Agent 搜了更多次”替代质量指标。固定检索与自主检索都跑同一数据集，同时比较命中、最终答案、延迟和工具成本。按需加载的思路及额外探索成本在 Anthropic 的上下文文章中有明确讨论。资料：Just-in-time context。

没有标准答案的题不要混入 recall 分母：它们用来测试“没有证据时是否停止编造”。召回失败与回答失败要分开：相关文档都没取到时，先修检索；取得证据却答错，再看选择与生成。

动手：让边界可观察

  1. 构造 D1=[构建,E42,插件]、D2=[构建,缓存]、D3=[登录,令牌]。查询 [构建]，k=1，相关集合=[D1,D2]。
  2. 计算 Recall@1，再用 [E42] 检索，相关集合改为 [D1]。
  3. 补一个语义相近但词项不同的问题“编译报错”，观察零命中。
  4. 画出自主检索时的两轮查询，给它设置最多 3 次查询；补一条证据不足时的最终回复。

验收：三个结果分别为 0.5、1、0（第三题相关集合非空）。能说明词项不同导致的失败，并没有把零命中直接变成事实性回答。

换个情境，还能做对吗？

自主检索最终正确率提高，但 p95 延迟翻倍。你会据此完全取消固定检索吗？

迁移题参考思路

不会。按问题类型分析：简单单跳问题可先做快速检索，出现证据缺口才授权追加探索。保留同一评估集，用质量、延迟和成本共同决定路由，而非按架构名称选型。
