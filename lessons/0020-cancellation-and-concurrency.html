取消、并发与过期结果

阻止旧运行覆盖新 UI，并区分停止接收、停止计算与撤销已发生动作。

阅读与判断 15–20 分钟实验 20–40 分钟资料核对：2026-09-22

前置：第 0019 课；Promise、AbortController 与组件卸载。

能力状态：通用工程机制；本文 TypeScript 是概念示意，未连接真实模型或生产存储。

本课服务于研发知识助手项目；页面备齐不代表已经掌握。以动手结果、解释和后续迁移作为学习证据。

取消有三个不同边界

用户提交 A，紧接着提交 B；B 先返回，A 后返回。若每次响应都直接 setState，A 会覆盖用户真正关心的 B。另一种情况是用户点了停止，浏览器断开连接，服务端却继续检索甚至已经完成写入。你需要分别定义：停止展示、请求取消运行、补偿已发生的副作用。

AbortController 可以向支持 signal 的操作发出中止信号，但不能让已经完成的外部动作倒退。DOM 规范定义的是取消机制，不是数据库事务回滚。资料：DOM AbortController。

先用运行身份挡住晚到结果

下面是“最新一次请求拥有 UI”的单界面策略。generation 只解决本页面的结果归属；服务端还要有独立 runId、持久取消标记，以及工具开始前的检查。并行运行可改成每个 run 一张独立卡片，不能共享一个 generation 造成互相覆盖。

let generation = 0;
let active: AbortController | undefined;
async function loadLatest(query: string, render: (text: string) => void) {
  const own = ++generation;
  active?.abort();
  const controller = new AbortController();
  active = controller;
  try {
    const response = await fetch("/api/search", {
      method: "POST", headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ query }), signal: controller.signal
    });
    if (!response.ok) throw new Error(`HTTP_${response.status}`);
    const text = await response.text();
    if (own === generation && !controller.signal.aborted) render(text);
  } catch (error) {
    if (own === generation && !controller.signal.aborted) throw error;
  }
}
function cancelLatest() { ++generation; active?.abort(); }

即使旧请求不响应 abort，generation 仍挡住它覆盖新结果；真正的网络错误不能统一吞掉，调用方应展示错误。对于流式 UI，要在每个事件进入 reducer 时检查 runId，而不是只在最后一次响应检查。

服务端确认才能显示“任务已停止”

取消请求先把 run 标为 cancelling；执行器观察标记后停止发起新的模型调用与工具，再报告 cancelled。已提交的外部操作可能进入 completed 或 unknown，要读回后报告真实结果。持久任务的恢复和检查点边界，可对照 LangGraph 的故障容错机制理解。资料：Fault tolerance。

状态提示应具体：“已停止生成，写入状态正在核对”比“已全部取消”准确。取消也可能与批准同时到达，服务器应使用事务或原子状态转移决定哪个事件先被接受，而不是让两个 HTTP 请求各自读旧状态后同时成功。

动手：让边界可观察

  1. 用两个可手动 resolve 的 Promise 模拟 A、B，让 B 先完成、A 后完成；不发网络请求。
  2. 把 fetch 临时换为这两个测试 Promise，并观察 generation 检查前后的渲染顺序。
  3. 写出“用户取消时写入已成功，但响应丢失”的 UI 文案和服务端处理。

验收：最终仅展示 B；取消后晚到文字不进入当前 UI；能说清 abort 没有证明外部写入被撤销。

建议先独立完成；本课代码用于理解机制。实验可在工作区新建笔记或 TypeScript 文件，真实 API 与依赖准备见 实验说明。

完成后查看参考解

发起 A 时 own=1，发起 B 时 own=2；B 完成时与 generation 相等，A 后完成时不等，被忽略。调用 cancelLatest 又增加 generation，所以当前请求的晚到结果也失去 UI 所有权。

副作用场景先标记结果未知，按 actionId 向外部系统读回。若已成功，就报告“生成已停止；此前提交的写入已完成”，提供真实结果。需要撤销时走独立的补偿动作，不能假装取消信号已经回滚。

换个情境，还能做对吗？

同一用户开了两个标签页，同时向同一会话发送不同需求。仅靠组件里的 generation 足够吗？

迁移题参考思路

不够。它只能保护一个页面。服务端要制定每会话单活动运行、串行排队或显式分支的策略，并用 runId 和状态版本约束提交；两个页面各自同步当前服务端状态。
