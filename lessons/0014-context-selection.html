05 · 上下文工程 · Lesson 0014

选择下一步真正需要的上下文

为下一次调用编排上下文预算，并写出能够保留限制、证据与未完成动作的压缩摘要。

阅读与判断 15–20 分钟实验 20–40 分钟资料核对：2026-09-22

前置：第 0013 课；理解 token 是模型计费和上下文长度的单位。

能力状态：通用工程机制；本文 TypeScript 是概念示意，未连接真实模型或生产存储。

本课服务于研发知识助手项目；页面备齐不代表已经掌握。以动手结果、解释和后续迁移作为学习证据。

上下文工程是每一步的选择

知识助手已经检索了三份文档，现在要判断某次构建失败的原因。把三份全文、五十次旧搜索和整段聊天都发送给模型，会把真正关键的错误信息淹没。上下文工程要回答的是：这一步决定下一项动作，需要哪些材料？Anthropic 的工程文章讨论了按需读取、压缩和结构化笔记；它们是可组合的策略，不能只凭“窗口更大”假定效果更好。资料：Context engineering。

对本项目，先保留当前目标、用户限制、工具安全规则和未完成调用，再选择相关证据。已经读过的长输出可换成来源路径、版本和关键定位，必要时用工具重读。这里的“必须保留”由应用规则定义，不能让检索分数把用户的“只读，不修改”挤出去。

先预留预算，再装材料

下面把输入按完整块选择。token 数来自调用方使用的模型计数器；代码里的 budget 是教学参数，不对应任何厂商的窗口上限。工具调用和结果需要按提供商要求成组保留，不能在 JSON 中间按字符截断。

type Block = {
  id: string; tokens: number; priority: number; required: boolean;
};
function selectContext(blocks: Block[], budget: number): Block[] {
  const picked = blocks.filter(b => b.required);
  let remaining = budget - picked.reduce((n, b) => n + b.tokens, 0);
  if (remaining < 0) throw new Error("REQUIRED_CONTEXT_TOO_LARGE");
  for (const b of blocks.filter(b => !b.required)
      .sort((a, b) => b.priority - a.priority)) {
    if (b.tokens <= remaining) { picked.push(b); remaining -= b.tokens; }
  }
  return picked;
}

例如上下文预算 4,000 token，先扣除规则和当前问题 1,200，再扣除输出预留 800，本轮证据可用 2,000。这里只是教学算例；实际应按照提供商的上下文与输出计算规则计数。检索库中存着 20 MB 内容与这一轮发送了多少 token 是两件事。

压缩必须保留可恢复性

一份好摘要应至少说明目标、仍有效的约束、已验证结论及来源、已尝试但失败的方案、未决问题、下一步。把“工具计划写入文件”压成“已写入文件”会制造假状态。摘要应附原事件范围和来源版本；有争议时回到原记录核对。LangChain 的记忆说明也强调长历史中的过时信息会影响使用，删减策略应服务当前任务。资料：Memory overview。

动手：让边界可观察

  1. 准备 5 个块：规则 600、当前问题 300、完整待处理调用 400、相关证据 A 900、历史日志 B 1,400 token。前三项 required=true，A 的优先级高于 B。
  2. 以 2,400 为输入预算运行选择逻辑，预测并核对结果。
  3. 把“用户只读；search 成功；read 超时；尚未找到原因”压成不超过 100 汉字的摘要。

验收：选择前三项加 A，共 2,200；摘要不能声称原因已定位，必须留下 read 超时及下一步。将 required 总量设为超过预算时明确失败，不能静默删规则。

完成后查看参考解

参考摘要：“目标：定位构建失败，限制：只读。已完成搜索，候选见事件 e12 的文档路径；读取正文超时，尚无根因证据。下一步重试授权范围内的读取；再次失败则报告缺失信息。原记录 e1–e13。”预算输出为 rules、question、pending、A；B 因放不下被省略。

压缩后的摘要不是权威来源；长期运行时还应检验它能否支撑下一步正确行动，而非只看缩短了多少 token。
