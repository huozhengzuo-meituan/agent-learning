工具权限与执行隔离

把工具能力做成最小权限，并说明代码执行需要哪一层隔离。

阅读 10–15 分钟 · 练习 20–40 分钟来源核对：2026-09-22应用侧 · TypeScript

本课交付：把工具能力做成最小权限，并说明代码执行需要哪一层隔离。

前置：0008 实现一个受约束的只读工具、0021 把人工确认做成程序约束、0027 识别提示注入与信任边界

场景统一使用虚构文档与工单。代码注明示意时，需要接入你自己的项目上下文；本页不会发起模型调用。

先理解这个工程问题

“模型可以运行 TypeScript”会大幅扩展能力，也把文件系统、网络和进程变成风险面。先区分两层：业务授权决定允许处理哪个租户、哪份工单；执行隔离决定代码即使行为错误，也接触不到哪些资源。只在提示里写“不要读取密钥”不构成隔离。

Node.js 官方明确说明 node:vm 不是安全机制。TypeScript 类型检查同样不限制运行时网络请求。课程里的 runCode 接口是能力模型示意；不能把字符串交给 eval 后就称为安全沙箱。生产方案需采用适合威胁模型的隔离执行环境、资源配额、网络出口策略与凭证代理。

为助手先提供一个只读搜索能力，再提供需要审批的草稿保存能力，比暴露任意 HTTP 与任意 Shell 更容易审核。授权范围由宿主构造并在每次调用时检查，沙箱只获得必要的数据和短期能力；不把长期服务凭证放入模型可执行代码的环境。

Docker 的安全文档讨论 namespace、capability 等机制及隔离边界；“放进容器”不等于完成沙箱设计。挂载宿主根目录、共享 Docker socket、默认放行全部网络，都会破坏预期边界。具体失败案例是只允许导出摘要，却把包含所有租户资料的目录挂进了同一个容器。

读一段代码或执行轨迹

先预测输出或指出边界，再对照注释。以下为课程教学片段；基础机制的可运行实验见 实验说明。本课特定集成需按练习自行实现，未声称已运行。

// 课程自定义的声明；必须由真正的执行环境落实。
type SandboxPolicy = {
  readableArtifacts: readonly string[];
  writableDirectory: string;
  networkHosts: readonly string[];
  deadlineMs: number;
  maxOutputBytes: number;
};
const summarizePolicy: SandboxPolicy = {
  readableArtifacts: ["artifact:demo/release-7"],
  writableDirectory: "/workspace/output",
  networkHosts: [],
  deadlineMs: 3000,
  maxOutputBytes: 16000
};
// 仅声明 policy 不产生隔离；禁止把它误当作沙箱实现。

动手：把判断变成证据

  1. 列出 summarize 工具最少需要的文件、网络、时间和输出能力。
  2. 设计四个拒绝场景：访问未授权资料、联网、无限循环、输出超过配额。
  3. 为每个场景指定真正的执行者：资源服务、网络出口、沙箱调度器或输出通道；不能全部填“提示词”。

验收：每个权限都有执行层归属和拒绝证据；能说明本地夹具只能测试策略，不能证明操作系统隔离可靠。

完成后再展开：参考解与检查思路

资料访问由资源服务按租户验证，联网在沙箱网络出口阻止，超时由外部调度器终止执行，输出通道限制字节数并返回明确截断状态。若所有工具都通过受控代理，代码不需要拿到上游服务的长期密钥。
