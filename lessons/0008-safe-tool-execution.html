03 · 工具与执行循环 · LESSON 0008

实现一个受约束的只读工具

把工具契约变成受约束的只读执行器，在运行时检查输入、访问范围与输出大小。

阅读与检查 15–20 分钟动手任务 35 分钟资料核对 2026-09-22

这一课的具体成果

实现一个只能读取内存里已授权文档的函数，并用边界输入证明它不会任意读文件。

前置知识：完成第 0007 课，熟悉 unknown、类型缩窄、Map 和 Set。

执行器面对的是不可信参数

TypeScript 类型在运行时不会阻止模型或网络传入错误对象。工具入口应该从 unknown 开始，再检查对象、字段类型和长度。即使 SDK 已经做 schema 校验，工具内部的业务边界仍由你负责；特别是同一个执行函数可能被测试、后台任务或其他入口复用。

本课使用内存 Map 保存两份虚构组件文档，避免真实文件系统和外部请求。允许访问的 ID 由宿主传入的 ReadonlySet 决定。模型只能选择要读的 ID，不能修改允许集合，也不能把输入解释为路径。这个小实现足以练习权限边界，不需要先搭建完整服务。

把可访问范围放在可信上下文里

当前 AI SDK 区分模型工具输入与 per-tool context。本课先用普通函数参数演示同一原则：input 是候选意图，allowedIds 是宿主已计算好的范围。只有同时满足结构规则与访问规则，才可以读取内容。

不要通过 input.allowedIds 或 input.isAdmin 建立允许集合。即使提示里要求模型“只能读有权限的文档”，真正的约束仍需要执行代码。若以后文档来自数据库，访问检查应落到可信服务端与数据访问层，不能只依靠浏览器隐藏按钮。

只返回完成任务所需的内容

工具结果会被放进下一轮输入，因此它也需要大小控制。这里用字符上限演示截断，并明确标记 truncated。字符数不是 token 数，但作为本地防止巨大返回值的一层约束仍有价值。不能静默截断后让模型以为拿到了全文。

成功结果带有 docId 与 version，便于回答引用。不可访问和不存在合并为 NOT_AVAILABLE，避免额外透露文档状态。这个设计牺牲了一些对模型的精细诊断，但宿主日志仍可保留内部原因。真实产品应该根据数据敏感性决定公开错误语义。

把过程放进 TypeScript

这是独立的 TypeScript 教学片段，无 SDK、文件系统或网络依赖。片段未作为课程自动测试执行；请按练习的输入自行检查。

const docs = new Map([
  ["button-v2", { version: "2", text: "loading=true 时阻止重复点击。" }],
  ["dialog-v1", { version: "1", text: "关闭事件为 onClose。" }],
]);

function readDoc(input: unknown, allowedIds: ReadonlySet<string>) {
  if (!input || typeof input !== "object" || Array.isArray(input)) {
    return { ok: false as const, code: "INVALID_INPUT" as const };
  }
  const docId = (input as Record<string, unknown>).docId;
  if (typeof docId !== "string" || !docId || docId.length > 80) {
    return { ok: false as const, code: "INVALID_INPUT" as const };
  }
  if (!allowedIds.has(docId)) {
    return { ok: false as const, code: "NOT_AVAILABLE" as const };
  }
  const doc = docs.get(docId);
  if (!doc) {
    return { ok: false as const, code: "NOT_AVAILABLE" as const };
  }
  const maxChars = 2_000;
  return {
    ok: true as const, docId, version: doc.version,
    text: doc.text.slice(0, maxChars),
    truncated: doc.text.length > maxChars,
  };
}

readDoc({ docId: "button-v2" }, new Set(["button-v2"]));

即使输入 docId 是 ../../secret，该函数也只做 Map 查找，不会访问磁盘。允许集合必须由可信宿主创建；如果你直接把用户上传的集合传进来，函数签名并不会自动使它可信。

动手：用四个输入检验边界

  1. 在本地 TypeScript 练习里复制函数，分别传入 null、数字 docId、未授权的 dialog-v1、已授权的 button-v2。
  2. 增加一份超过 2,000 字符的虚构文档，检查 text 长度与 truncated 是否一致。
  3. 把 allowedIds 从空集合改成仅含 button-v2，说明这项改变来自哪里、谁不应该控制它。
验收条件

错误形状得到 INVALID_INPUT；未授权 ID 得到 NOT_AVAILABLE；允许的文档带版本返回；截断有明确标记；任何输入都不会触发文件或网络访问。

做过以后，再看参考答案

null 与数字字段应在读取前失败；未授权的 dialog-v1 即使存在也不返回正文；button-v2 在允许集合内才返回成功。长文档返回最多 2,000 个 JavaScript 字符单位并标记 truncated。这个上限不是 token 上限，也不是 Unicode 字素截断保证，实际面向展示时还需选择适合的文本边界。

停下来，从记忆里回答

工具的 allowedIds 应该由哪一方根据身份确定？

答案与理由

应选“可信宿主程序”。本课显式把模型参数与执行上下文分开，便于落实这个约束。

换个需求，还能用吗？

以后把 Map 改成数据库，哪些约束应保留，哪些地方需要重做？

迁移题参考要点

保留输入校验、身份范围、输出上限、来源与版本。重做数据库查询、访问控制与异常映射，并用参数化查询避免把 docId 拼成可执行查询语句。不要因为存储升级就把可信 allowedIds 改成用户可传入的字段。
