向量检索、分块与排序

解释分块如何影响证据完整性，并合并词法与向量候选得到可审计的排序。

阅读与判断 15–20 分钟实验 20–40 分钟资料核对：2026-09-22

前置：第 0015 课的召回基线；数组排序与 Map。

能力状态：通用工程机制；本文 TypeScript 是概念示意，未连接真实模型或生产存储。

本课服务于研发知识助手项目；页面备齐不代表已经掌握。以动手结果、解释和后续迁移作为学习证据。

语义相似只是候选，不是事实

向量把文本映射到数值空间，便于寻找语义接近的片段；“缓存没有更新”可能匹配“过期内容未失效”。但高相似度不代表它属于正确项目、版本或权限范围。错误码、函数名、版本号往往还需要词法匹配。Microsoft 的混合检索文档展示了合并全文与向量结果的设计。资料：Hybrid search。

不要把向量数据库当成 Agent 的所有记忆。它在这里的职责是提供候选，Agent 后续仍可按路径打开原文，检查缺失前提，或者发现文档过期。向量索引更新可以晚于原始文档，答案必须保留来源版本。

分块时留住“这段话在说谁”

一段只有“从 2.3 开始默认开启”的片段无法回答哪个功能。按标题、函数或完整条款分块，记录 documentId、section、version、contentHash、位置和权限信息；读取时可扩展相邻段落。Azure 的分块文档比较固定长度和结构分块，适合用来设计实验，而非把某个长度当成通用最优值。资料：Chunk documents。

合并排名，避免硬加异尺度分数

词法分数与向量相似度不在同一尺度，直接相加容易偏向某一侧。下面实现课程版 reciprocal rank fusion：每份排名按位置贡献 1 / (k + rank)，再合并同一 chunk。这里 k=60 是演示选择，要在你的数据上测量；输入必须已经完成权限过滤。

function fuse(rankings: string[][], k = 60): string[] {
  const scores = new Map<string, number>();
  for (const list of rankings) {
    [...new Set(list)].forEach((id, index) => {
      scores.set(id, (scores.get(id) ?? 0) + 1 / (k + index + 1));
    });
  }
  return [...scores].sort((a, b) => b[1] - a[1] ||
    a[0].localeCompare(b[0])).map(([id]) => id);
}
// 词法：A,B,C；向量：B,D,A；B 通常因两边排名靠前而上升。
const candidates = fuse([["A", "B", "C"], ["B", "D", "A"]]);

接下来可用 reranker 对候选与问题成对评分，只将少量结果交给模型。额外重排是否值得，取决于质量和耗时。Anthropic 的 Contextual Retrieval 介绍了给片段补充文档上下文的方法；这是 2024 年提出、仍可比较的索引技巧，本文不把它包装成 2026 年新标准。资料：Contextual Retrieval。

  3. 构造“旧版高相似度”和“新版稍低相似度”两个候选，设计版本过滤实验。

验收：返回顺序 B、A、D、C；证据能追溯原始文档位置。版本要求属于过滤或显式适用性判断，不能仅靠向量得分猜测。

B 得分为 1/62+1/61，A 为 1/61+1/63，所以 B 在前；D 和 C 分别只有 1/62、1/63。补充上下文示例：“项目 Atlas，重试功能，版本 2.3：从 2.3 开始默认开启”；引用保留原文位置，明确哪部分是标题补充，不把自动生成的补充当原文。

实验至少比较固定长度、按章节两种分块。保持查询集和其他参数不变，观察召回与答案支持率，避免同时改全部变量而无法归因。
