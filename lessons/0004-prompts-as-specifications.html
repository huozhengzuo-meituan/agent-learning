把提示写成可验证的任务规格

把“帮我回答得专业一点”改写为有输入边界、证据要求和可检查结果的任务规格。

阅读与检查 15–20 分钟动手任务 25 分钟资料核对 2026-09-22

这一课的具体成果

写出一份可用三个反例检查的组件文档问答提示，并说明代码还必须承担哪些约束。

前置知识：读懂第 0003 课调用片段，知道 instructions 与用户问题的位置。

提示首先是一份任务说明

“你是最资深的前端专家，请完美回答”没有告诉模型可依据什么，也没有定义资料不足时如何处理。把它换成工程规格：任务是什么、输入包含什么、哪些信息有来源、输出满足什么条件。这样做的收益是你能设计检查，而不是只能凭感觉评价措辞。

例如任务是解释 Button v2 的 loading。输入包含明确版本的文档片段，输出应说明点击行为并附文档标识。缺少 disabled 的说明时，应把这一点列为未知，而不是补出看似常见的组件行为。任务规格使“没有编造”成为可以逐条核验的约定。

给规则、数据和例子各自的位置

可信的应用规则放在服务端 instructions；用户问题与文档内容作为被处理的数据传入。当前 AI SDK prompts 文档使用这样的接口区分指令和消息。用清楚的分段或数据结构有利于理解来源，但分隔符本身不是权限系统，也不能保证抵御恶意内容。

示例应覆盖边界，而非只给一个永远成功的答案。例如同时给“文档支持结论”和“文档没有该属性”两种结果。过多风格指令会分散任务重点；本课只保留证据与不确定性规则。多轮 Agent 的上下文策略会继续变化，但这份任务规格应能作为可版本化的基础。

先写检查，再看答案

提示的改动需要有观察对象。本课使用三条小样本：文档明确支持、文档缺少说明、两份版本信息冲突。它们不是完整评估集，但足以暴露“每个问题都强行给肯定答案”的缺陷。先写预期边界，再比较输出，能避免看到流畅答案后临时放宽标准。

不要要求公开模型全部内部推理来当作正确性证据。对用户真正有用的是简洁解释、可查来源与限制。输出引用是否存在、版本是否匹配，可以用程序检查；最终解释是否由文档支持，还要结合样本评估。提示负责描述期望，程序负责可靠执行硬约束。

把过程放进 TypeScript

这是自定义的提示构造片段，不会发起 API 调用。把规则与待处理材料分开，后续可将它们传给第 0003 课的调用函数。

const instructions = [
  "任务：回答虚构组件文档问题。",
  "只依据本次提供的文档，不补写未知属性。",
  "先给结论，再列出支持结论的文档 ID。",
  "版本冲突时指出冲突，缺少资料时说明缺什么。",
].join("\n");

const input = {
  question: "Button v2 的 loading 是否阻止点击？",
  documents: [
    {
      id: "button-v2",
      version: "2",
      text: "loading 为 true 时阻止重复点击。",
    },
  ],
};

const prompt = JSON.stringify(input);

JSON.stringify 是序列化数据，不会把不可信文字变成可信指令。这里也没有宣称 JSON 形式优于所有文本格式：它只是让题目、文档标识和版本清楚可见，便于你检查输入。

动手：写提示，再用反例挑战它

  1. 为上面的问答任务写一版最多六条规则的 instructions。
  2. 准备三个输入：loading 有证据、disabled 无证据、v1 与 v2 行为不同且用户没给版本。
  3. 每条输入先写期待出现和禁止出现的结论；没有 API 时，手工写一份可能的错误输出并判定其违反哪条规则。
验收条件

每个样本都有具体判断标准；无证据样本不会被要求猜测；版本不明确样本能够澄清或分版本回答；不把“语气专业”当作唯一标准。

做过以后，再看参考答案

有证据：说明 loading=true 阻止重复点击，引用 button-v2。无证据：说明当前材料没有 disabled 规则，需要补文档。版本冲突：明确分开 v1、v2 的规则，询问实际使用版本，不能混成一个答案。规则长度可以不同，但每条都应能对应一个可观察行为。

答案与理由

应选“结论有据可查”。风格可以是产品要求，但不能替代事实与来源检查。

换个需求，还能用吗？

把任务改为“根据工单写发布摘要”，你会保留哪两类规格，又增加什么？

迁移题参考要点

保留输入来源与缺失信息处理、输出验收条件。增加摘要的目标读者、工单范围和禁止推断的字段，例如未给出的上线时间、影响人数和修复版本。不要让模型把待处理工单自动写成已发布。
