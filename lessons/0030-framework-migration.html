把手写循环映射到框架

把手写 Agent 循环迁入框架，同时用契约测试保持行为边界。

阅读 10–15 分钟 · 练习 20–40 分钟来源核对：2026-09-22应用侧 · TypeScript

本课交付：把手写 Agent 循环迁入框架，同时用契约测试保持行为边界。

前置：0009 亲手读懂并补完 Agent 循环、0010 让任务在正确的时候停止、0021 把人工确认做成程序约束、0024 评分器、重复试验与回归判断、0029 MCP 连接了什么，留下了什么

场景统一使用虚构文档与工单。代码注明示意时，需要接入你自己的项目上下文；本页不会发起模型调用。

先理解这个工程问题

框架的价值是减少反复实现循环、消息拼装、流式事件与类型推断的工作。迁移前先列清楚手写循环已经承诺的行为：最大步骤、允许工具、取消、错误传播、审批、证据 ID、停止原因。框架省掉了多少代码，与这些承诺是否仍成立，要分开判断。

当前 AI SDK 的 ToolLoopAgent集中配置模型、instructions 和工具；循环控制使用 stopWhen 与 prepareStep，本次文档的步数条件名为 isStepCount。具体 API 绑定当前文档，安装时必须按锁定版本核对，不能把旧教程的参数名直接混用。

最大模型步骤并不等于最大工具执行次数：一个模型响应可能请求多个工具；费用和执行次数仍要在工具网关独立计数。框架内置的停止条件也不能替代业务完成判据。能生成最终文字，不等于文档证据齐全或草稿已通过审批。

具体失败场景：迁移后工具函数直接写工单，原来在执行器中的审批被绕过；界面仍显示一个确认按钮，但后端已经执行。先用同一份假模型轨迹测试两个实现，再连接真实模型。迁移应按“调用模型、提出动作、批准动作、执行动作”分别观察。

读一段代码或执行轨迹

先预测输出或指出边界，再对照注释。以下为课程教学片段；基础机制的可运行实验见 实验说明。本课特定集成需按练习自行实现，未声称已运行。

// API 形状示例：需安装匹配版本的 ai 并配置 model/tools 后使用。
import { ToolLoopAgent, isStepCount } from "ai";

// model 与 tools 由你的应用注入；工具网关继续负责身份、预算和审批。
function createAssistant(
  model: ConstructorParameters<typeof ToolLoopAgent>[0]["model"],
  tools: ConstructorParameters<typeof ToolLoopAgent>[0]["tools"]
) {
  return new ToolLoopAgent({
    model,
    instructions: "按证据回答；没有证据时说明缺口。",
    tools,
    stopWhen: isStepCount(8)
  });
}
// 这段不包含真实调用；不等于已经完成供应商集成验证。

动手：把判断变成证据

  1. 写一张映射表：历史消息、工具 schema、执行器、停止条件、事件流分别交给哪层。
  2. 准备四条固定轨迹：正常检索、持续调用工具、审批被拒绝、调用过程中取消。
  3. 在迁移前后比较工具实际调用次数、最终停止原因与写入次数；不能只比较回答文本。

验收：四条轨迹的安全与业务结果一致；能说明哪些差异只是框架事件名，哪些是行为回归。

完成后再展开：参考解与检查思路

把审批与幂等封装在受控工具网关，框架仅请求执行。持续调用轨迹应在限定步数终止，且被拒绝写入的次数始终为零；取消后的结果不能覆盖新任务。若框架行为不支持某契约，先保留适配层再评估是否迁移。
