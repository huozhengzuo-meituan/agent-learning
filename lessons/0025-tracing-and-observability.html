用执行轨迹定位问题

从一次失败任务的执行轨迹，指出第一个偏离预期的步骤。

阅读 10–15 分钟 · 练习 20–40 分钟来源核对：2026-09-22应用侧 · TypeScript

本课交付：从一次失败任务的执行轨迹，指出第一个偏离预期的步骤。

前置：0009 亲手读懂并补完 Agent 循环、0023 建立有代表性的评估任务集、0024 评分器、重复试验与回归判断

场景统一使用虚构文档与工单。代码注明示意时，需要接入你自己的项目上下文；本页不会发起模型调用。

先理解这个工程问题

知识助手回答“未找到发布说明”，但库里明明有文档。只看最终回答，无法区分模型没检索、检索参数错误、权限过滤或结果丢失。先把任务拆成可观察操作：任务是一个 trace，模型请求、检索与工具执行各是一段 span，父子关系表示谁触发了谁。这个结构来自 OpenTelemetry 的 trace/span 模型。

我们为每次任务记录 runId、步骤序号、操作名、耗时、结果类型，以及模型、提示、工具契约的版本。文档正文和用户问题默认不写入日志；记录文档 ID 与内容版本即可定位多数问题，需要原文时再使用受控的诊断通道。日志是执行证据，不是模型隐含思维的录音。

本课案例：检索返回 3 个文档，过滤后剩 0 个，原因是运行上下文错误地使用了另一个租户。第一处异常是授权上下文构造；换模型无法修复它。另一种情况是返回 3 个合法结果却未进入下一轮上下文，那就追查消息组装。先定位分界，再提出可验证假设。

当前 AI SDK telemetry 文档使用注册集成的方式接入 OTel，注册后默认记录调用事件，并提供关闭输入、输出记录的选项。具体配置随 SDK 版本变化；下面用自定义事件结构练习诊断，不依赖某个 SDK。

读一段代码或执行轨迹

先预测输出或指出边界，再对照注释。以下为课程教学片段；基础机制的可运行实验见 实验说明。本课特定集成需按练习自行实现，未声称已运行。

type TraceEvent = {
  runId: string; step: number; operation: string;
  outcome: "ok" | "error"; resultCount?: number;
  reason?: string;
};
const events: TraceEvent[] = [
  { runId: "r7", step: 1, operation: "search", outcome: "ok", resultCount: 3 },
  { runId: "r7", step: 2, operation: "authorize", outcome: "ok", resultCount: 0,
    reason: "tenant_mismatch" },
  { runId: "r7", step: 3, operation: "answer", outcome: "ok" }
];
// 工具执行成功，不等于业务任务成功。
const firstSuspect = events.find(e => e.reason !== undefined);
console.log(firstSuspect?.step); // 2

动手：把判断变成证据

  1. 为上面的轨迹补上“传入的租户由哪个服务端身份派生”这一条事件；只用虚构标识。
  2. 另造一条检索成功但上下文组装丢失结果的轨迹，用同一组字段区分两个故障。
  3. 为两条轨迹分别写一句根因假设和一个验证动作；检查日志中没有文档原文或凭证。

验收：给出两个不同修复位置；能解释 outcome=ok 为什么仍可能导致任务失败；每条判断都能指向一个事件。

完成后再展开：参考解与检查思路

第一条在创建运行上下文时核对已认证用户与 tenantId 的映射，不能删除权限过滤。第二条对比检索输出的文档 ID 与下一次模型输入中的证据 ID。给 trace 增加证据数量和版本即可验证，无需默认保存全部敏感文本。

迁移题参考答案

不能只按答案计成功。应分别记业务结果与策略违规尝试，并验证执行层确实拦截。把此轨迹加入安全回归集，避免最终文本掩盖过程问题。
