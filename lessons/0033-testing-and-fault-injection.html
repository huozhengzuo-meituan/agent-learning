通过故障注入检验系统边界

用可控故障证明授权、停止、幂等和恢复契约确实有效。

阅读 10–15 分钟 · 练习 20–40 分钟来源核对：2026-09-22应用侧 · TypeScript

本课交付：用可控故障证明授权、停止、幂等和恢复契约确实有效。

前置：0011 区分失败类型，再决定是否重试、0022 检查点、恢复与幂等、0024 评分器、重复试验与回归判断、0025 用执行轨迹定位问题

场景统一使用虚构文档与工单。代码注明示意时，需要接入你自己的项目上下文；本页不会发起模型调用。

先理解这个工程问题

正常路径只能证明系统在顺利时会工作。Agent 的错误经常发生在边界：工具已经写入但响应丢失、模型持续要求重试、审批后参数又被修改、进程在保存状态之前崩溃。测试需要主动制造这些时刻，观察外部效果。

把测试分成确定性的运行时契约与统计性的模型评估。假模型可以精准输出连续三次同样的工具调用，用来验证去重；它不能证明真实模型会稳定选择正确工具。真实任务要在固定评分标准下重复运行，记录成功分布。Agent evals 的实践文章区分轨迹、最终环境状态与评分器，这正好帮助我们选择断言位置。

写入幂等必须在产生副作用的一侧成立。下面的 Set 只是单进程实验夹具；生产系统需要持久幂等键、原子性与并发控制。若先写工单后记录幂等键，崩溃窗口仍会重复写入。测试不能用一种碰不到竞态的实现来“证明”分布式正确性。

具体失败：第一次请求实际新增了草稿但网络超时，第二次换了一个随机幂等键；最终出现两份相同草稿。正确修复是把同一个业务动作的键保存并重用，而不是把全局重试次数设为零。Node 的内置测试运行器足以开始这些离线契约测试。

读一段代码或执行轨迹

先预测输出或指出边界，再对照注释。以下为课程教学片段；基础机制的可运行实验见 实验说明。本课特定集成需按练习自行实现，未声称已运行。

// 单进程、同步内存夹具；只演示相同动作使用同一个键。
const applied = new Set<string>();
let writes = 0;
function applyDraft(key: string) {
  if (!applied.has(key)) {
    applied.add(key);
    writes += 1;
  }
  return { key };
}
applyDraft("tenant-demo:run-3:draft-1");
// 模拟结果丢失后重试：仍传同一 key。
applyDraft("tenant-demo:run-3:draft-1");
if (writes !== 1) throw new Error("DUPLICATE_WRITE");

动手：把判断变成证据

  1. 建四个测试：已写入后超时、恢复后重复派发、审批过期、连续无进展工具请求。
  2. 每个测试先写不可变约束，例如“审批过期时写入次数为零”，再注入故障。
  3. 分别说明夹具证明了什么，以及仍需持久存储或真实模型测试的部分。

验收：每种故障都有一个外部状态断言与一个停止原因断言；测试失败时能定位策略层；不把 mock 通过写成真实模型准确率。

完成后再展开：参考解与检查思路

已写入后超时与重复派发共用持久动作键，检查只有一份草稿。审批过期返回 needs_approval，不能继续写入。连续无进展在预算边界结束并保留已有证据。再增加两个 worker 同时恢复的测试来暴露租约竞争。

检索练习：不看上文作答

写入成功但响应丢失，重试应如何处理动作键？

答案与原因（离线、无脚本也可阅读）

答案：继续使用原键。同一个业务动作必须沿用原键；否则接收端无法识别这是重试。

换个场景再判断

所有离线测试通过，真实模型仍会引用错文档，是不是测试无用？

迁移题参考答案

离线测试证明运行时边界，不覆盖所有模型行为。把错误任务加入固定评估集，核对检索、上下文与证据对应评分；保留契约测试，同时增加针对实际失败的模型评估。
