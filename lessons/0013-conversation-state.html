会话状态与用户隔离

实现一个按租户、用户和会话授权读取的状态入口，解释“数据库里有历史”和“模型能看到历史”的区别。

阅读与判断 15–20 分钟实验 20–40 分钟资料核对：2026-09-22

前置：第 0009 课的执行循环；TypeScript 对象、Map 和 Promise。

能力状态：通用工程机制；本文 TypeScript 是概念示意，未连接真实模型或生产存储。

本课服务于研发知识助手项目；页面备齐不代表已经掌握。以动手结果、解释和后续迁移作为学习证据。

会话不是一串可以随意转发的消息

在研发知识助手里，用户 A 正在分析项目甲，用户 B 正在分析项目乙。浏览器都提交了 threadId="today"。如果服务端只按这个字符串取历史，两个人的上下文就会混在一起。另一个常见错误是相信客户端传来的完整消息数组：攻击者可以塞入伪造的工具结果，让模型以为它已经读过某份私有文档。

本课把三层状态分开：持久会话保存授权范围内的事件；运行状态保存当前任务的步骤、预算和待完成调用；模型输入是运行时本次挑出的材料。LangGraph 的官方文档区分线程检查点和跨线程 Store，这个划分可借来理解职责，但不会自动替应用实现用户鉴权。资料：Persistence。

身份来自服务器，会话标识来自请求

服务端先从已验证的登录态获得 principal，再读取会话并检查归属。会话 ID 即使很难猜，也不等于访问权限。不要让模型选择 tenantId；它只负责业务推理。下面通过返回副本避免调用方意外修改仓库，实际服务还要用数据库的事务或版本检查处理并发写入。

type Principal = { tenantId: string; userId: string };
type Thread = Principal & {
  id: string; revision: number; events: string[];
};
function readThread(
  store: Map<string, Thread>, actor: Principal, id: string
): Thread {
  const row = store.get(id);
  if (!row || row.tenantId !== actor.tenantId ||
      row.userId !== actor.userId) {
    throw new Error("THREAD_NOT_FOUND_OR_FORBIDDEN");
  }
  return structuredClone(row);
}

把状态存下来也不代表全部塞进下一次请求。模型只看到你实际发送的内容；运行时可保留原始事件，仅把当前目标、已核对事实和近期完整调用放入上下文。跨会话记忆另走范围明确的读取入口，不能默认合并同公司所有聊天。资料：Memory overview。

追踪一次请求：登录态 → 会话归属检查 → 加载已提交事件 → 选择模型输入 → 执行循环 → 按 revision 提交。授权要发生在读取内容之前；权限撤销后，缓存也必须失效。

动手：让边界可观察

  1. 建立 A、B 两名用户，同一租户下分别拥有 t-a、t-b，每条会话写入不同的项目名。
  2. 用 A 读取 t-a、t-b、不存在的 ID；再以不同租户的同名用户读取 t-a。
  3. 在纸上画出“数据库保存 30 条事件，本轮模型只收到 8 条”的数据流。注明筛选在哪一层。

验收：仅第一种读取成功；其他读取不返回历史内容。修改返回对象后，再读原对象应不变。写下为什么客户端提交的 assistant/tool 消息不能直接视为可信记录。

建议先独立完成；本课代码用于理解机制。实验可在工作区新建笔记或 TypeScript 文件，真实 API 与依赖准备见 实验说明。

完成后查看参考解

成功案例的 actor 和 row 的两个归属字段都一致。跨用户和跨租户访问应在返回内容前失败。筛选在服务端构建模型请求的步骤执行，原始事件继续留在持久存储供审计和恢复。客户端提供的是请求数据；只有服务器自己核实并记录的工具执行结果才可作为执行证据。

进一步实现时，更新条件包含 revision === expectedRevision，冲突后重新加载状态；不能把上一次读取的整条历史无条件覆盖回去。

不看上文，检验一次

攻击者知道了别人的会话 ID，服务端的首要约束是什么？

答案与理由（无脚本时也可查看）

答案：重新校验用户权限。身份和资源归属属于服务端授权。会话 ID 和系统提示都无法替代这个检查。

换个情境，还能做对吗？

同一用户切换到另一个公司空间时，用户 ID 不变。仅按 userId 缓存“上次使用的仓库”会发生什么？

迁移题参考思路

旧空间的仓库信息可能进入新空间。缓存键和记忆命名空间至少包含 tenantId、userId 与用途范围，并在读取原资源时再次检查当前权限。
