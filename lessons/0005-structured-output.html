02 · 可用的模型接口 · LESSON 0005

把模型输出变成可校验的数据

把自然语言回答转换为可校验的数据，并明确区分结构正确与业务正确。

阅读与检查 15–20 分钟动手任务 30 分钟资料核对 2026-09-22

这一课的具体成果

设计一个“结论 + 文档 ID + 是否缺资料”的返回结构，再用两个非法样本检验它。

前置知识：理解 TypeScript 类型和第 0004 课的任务规格；知道 JSON.parse 的基本用途。

类型声明不会检查网络数据

把模型输出写成 JSON.parse(text) as Answer，只是告诉 TypeScript 相信你的断言。它没有验证返回对象是否真的有 answer 字段，也没有防止 citations 变成数字。模型输出和任何外部 API 响应一样，进入业务逻辑之前需要运行时校验。

第一层检查是合法 JSON；第二层是字段类型与取值；第三层才是业务规则。JSON.parse处理第一层；它不能证明某个文档 ID 存在，更不能证明回答忠实于该文档。学会拆开这三层，错误处理才会有针对性。

让生成与校验使用同一份结构

当前 AI SDK 的结构化输出文档使用 generateText 的 output 配合 Output.object 指定结构。下面的 schema 同时表达给模型的输出形状和应用要接收的数据类型。具体模型对结构约束的支持仍需核对，结构化生成不是取消错误处理的理由。

字段应对应产品需要。我们的答案只需要结论、引用文档 ID 和缺资料标记，不需要模型自行生成“系统确认正确”的标签。模型报告的不确定性可作为信息，但不替代程序或评估的质量判断。让每个字段都有消费者，避免为了看起来完整而增加无法验证的字段。

校验通过，还没完成验收

即使 citations 是合法字符串数组，里面也可能出现从未提供的 button-v99。业务层应将引用与本轮允许的文档集合核对。这个检查能够拒绝不存在的来源，但不能自动判断一段答案是否由真实来源支持；后者需要进一步规则或评估。

失败也要分类：输出无法解析、schema 不匹配、引用不存在，以及结构合法但事实不成立。它们需要不同修复。不要在解析失败时默默返回空对象，那会把上游失败推迟成下游难以理解的 UI 错误。第 0011 课会区分可重试失败与需要修改输入的失败。

把过程放进 TypeScript

官方结构化输出接口片段，未执行真实 API。model 由第 0003 课的服务端适配器配置；这里单独展示结构与引用检查。

import { generateText, Output } from "ai";
import { z } from "zod";

const AnswerSchema = z.object({
  answer: z.string(),
  citations: z.array(z.string()),
  missingEvidence: z.boolean(),
});

// model 是预先配置的服务端模型实例
async function generateAnswer(model: Parameters<typeof generateText>[0]["model"]) {
  const { output } = await generateText({
    model,
    output: Output.object({ schema: AnswerSchema }),
    prompt: "依据 button-v2：loading=true 阻止重复点击。解释 loading。",
    maxRetries: 0,
  });

  const allowedIds = new Set(["button-v2"]);
  if (output.citations.some(id => !allowedIds.has(id))) {
    throw new Error("回答引用了本轮未提供的文档");
  }
  return output;
}

示例中的 schema 只做必要的形状校验；它没有规定“非缺资料答案至少一条引用”，也没有核对引用对结论的支持程度。这两点就是你接下来要补上的业务验收。

动手：用坏样本检验返回契约

  1. 设计三个 JSON 样本：citations 是数字；citations 包含 button-v99；结论说“不阻止点击”但引用 button-v2。
  2. 对每个样本指出最早能发现问题的层：解析、结构或业务语义。
  3. 补写规则：missingEvidence 为 false 时，citations 至少有一条；不要把“至少一条”误写为“事实一定正确”。
验收条件

三种失败能被分别描述；能说明类型断言不等于运行时校验；引用有效与结论正确没有混为一谈。

做过以后，再看参考答案

citations 为数字属于 schema 失败；button-v99 属于引用集合检查失败；与文档相反的结论属于事实支持检查失败。补充业务规则可以写为 if (!output.missingEvidence && output.citations.length === 0) throw new Error('缺少引用')。这仍需要对实际回答与文档进行核对。

答案与理由

应选“字段结构有效”。这里的 schema 只定义字段和类型，业务事实与证据支持需要进一步检查。

换个需求，还能用吗？

模型返回工单分类 {category: 'bug', priority: 'P0'} 且结构合法。可以立刻触发全员告警吗？

迁移题参考要点

还不能。优先级的业务标准、证据与操作权限需要额外判断；P0 字符串符合枚举不意味着事故严重度已经确认。可以先把它当作候选分类，再走明确的业务审核或规则判断。
