把执行事件映射为前端状态

用可重放事件驱动 UI，正确显示工具执行、等待批准和最终完成，而不靠模型文案猜状态。

阅读与判断 15–20 分钟实验 20–40 分钟资料核对：2026-09-22

前置：第 0006 课的流式事件；熟悉 React reducer 或类似状态管理。

能力状态：应用事件模型为课程设计；AI SDK 文档按 2026-09-22 核对，接入时需匹配具体依赖版本。示例未联调。

本课服务于研发知识助手项目；页面备齐不代表已经掌握。以动手结果、解释和后续迁移作为学习证据。

聊天气泡承载不了完整执行状态

Agent 一边输出说明，一边调用检索工具，还可能等待用户批准。若界面只看是否收到文字，“正在提交”会被误显示成“提交成功”。前端应该呈现服务端确认的执行事件，模型文字作为可读内容单独渲染。

AI SDK 的 UI 文档展示了消息 parts 与流式事件，说明一条消息可含文本、工具和数据。资料：Chatbot。下面使用自定义课程事件，不是该 SDK 的真实协议；你可以在适配层把所选 SDK 的事件映射为本项目模型。

状态转移由事件定义

先写清不同层次：连接状态是连接中/断开；run 状态是运行/待批准/完成/失败；每个 toolCall 有自己的状态。某个工具返回并不说明整个 run 完成，文字流结束也不说明外部写入已经成功。并行工具应按 callId 单独显示卡片。

type Status = "running" | "waiting" | "completed" | "failed";
type View = { runId: string; seq: number; text: string; status: Status };
type RunEvent = { runId: string; seq: number } & (
  | { type: "text"; delta: string }
  | { type: "status"; status: Status }
);
function reduce(view: View, event: RunEvent): View {
  if (event.runId !== view.runId || event.seq <= view.seq) return view;
  if (event.seq !== view.seq + 1) throw new Error("REPLAY_GAP");
  if (view.status === "completed" || view.status === "failed") return view;
  return event.type === "text"
    ? { ...view, seq: event.seq, text: view.text + event.delta }
    : { ...view, seq: event.seq, status: event.status };
}

服务端在一个 run 内分配连续序号，重连时按 cursor 重放，重复事件可忽略；发现缺号则请求补齐或重新获取快照。例子遇到缺口直接抛错，实际 UI 应捕获并显示“同步中”，不能直接崩溃。业务事件是否可重放取决于你的持久日志，SSE 本身不会替你保存历史。

协议也要区分文字块的开始、增量和结束，避免把同一个块重复拼接。AI SDK 的流协议提供这类结构，接入时应使用与依赖版本匹配的解析器。资料：Stream protocols。

前端可验收体验：用户能看到当前动作、证据卡片、待批准内容与失败后的恢复入口。不要把私密推理链作为产品必需的日志；提供面向用户的简要执行状态与可核对结果即可。

动手：让边界可观察

  1. 初始化 run=r1、seq=0、text=""、status=running。依次输入 seq1 文字“找到”、seq2 文字“文档”、seq3 waiting。
  2. 重复 seq2，再输入 r0 的旧事件，确认状态未改变。
  3. 跳过 seq4 直接传 seq5 completed，模拟补齐或重读快照。
  4. 纸上画出一个工具失败、另一个成功时的 UI；整个 run 仍可继续。

验收：文本只出现一次“找到文档”；缺号触发同步处理。成功标签只由最终业务事件显示，不能被“我已经完成”这样的文字触发。

建议先独立完成；本课代码用于理解机制。实验可在工作区新建笔记或 TypeScript 文件，真实 API 与依赖准备见 实验说明。

完成后查看参考解

seq3 后应显示 waiting，重复事件被去重，其他 run 的事件被隔离。seq5 在没有 seq4 时触发 REPLAY_GAP；客户端捕获后请求缺失事件，或用服务端快照替换状态。工具卡片分别标识成功/失败，run 状态由下一步是否仍能完成任务决定。

生产适配层还应拒绝未知事件类型、校验字段，并在服务端持久化终态；浏览器刷新后不能只靠内存猜测任务状态。

答案与理由（无脚本时也可查看）

答案：服务端的执行事件。UI 的业务状态来源于经过执行器确认的事件。语言表达不能证明外部动作成功。

迁移题参考思路

检查批准请求是否有稳定 actionId 与当前服务器状态，消息内容和业务状态是否分开恢复。渲染按钮前读取 action 的待批准状态；客户端重放不能重新创建审批请求。
