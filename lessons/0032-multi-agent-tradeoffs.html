何时值得引入多个 Agent

通过任务依赖与评估结果，决定使用并行工具还是多个 Agent。

阅读 10–15 分钟 · 练习 20–40 分钟来源核对：2026-09-22应用侧 · TypeScript

本课交付：通过任务依赖与评估结果，决定使用并行工具还是多个 Agent。

前置：0024 评分器、重复试验与回归判断、0025 用执行轨迹定位问题、0026 测量并优化任务成本与延迟、0031 长任务的计划与运行支撑

场景统一使用虚构文档与工单。代码注明示意时，需要接入你自己的项目上下文；本页不会发起模型调用。

先理解这个工程问题

多个 Agent 的直接收益通常来自独立探索、独立上下文或职责边界，而不是数量本身。比较三个发布模块时，三个子任务可以各自检索证据；修改同一份工单草稿时，多个作者同时写入反而增加冲突。先画依赖，再选择并行方式。

如果只是已知的三次只读搜索，普通 Promise.all 就能并行；如果每个分支都要根据检索结果决定下一步，才有理由给它独立 Agent 循环。Anthropic 的多 Agent 研究系统给出这种独立研究分支的实践，但其收益与成本不能直接套用到短问答。

任务委派应包含目标、允许资源、输出 schema、预算和终止条件。子 Agent 返回证据与不确定项；主 Agent 负责对齐口径和最终验收。子 Agent 的信心不是证据，相互投票也不能替代独立可检验的事实。共享写入通过一个协调者进行。

具体失败场景：三个子 Agent 都只读到同一篇过期文档，却给出一致答案。增加人数没有增加信息。另一种失败是父任务取消，子任务继续消耗预算。实现要向下传播取消信号，汇总实际费用，限制总并发；使用 独立评估角色时也要校准评分偏差。

读一段代码或执行轨迹

先预测输出或指出边界，再对照注释。以下为课程教学片段；基础机制的可运行实验见 实验说明。本课特定集成需按练习自行实现，未声称已运行。

type ResearchResult = {
  module: string; evidenceIds: string[]; unresolved: string[];
};
async function gather(
  modules: string[],
  research: (module: string, signal: AbortSignal) => Promise<ResearchResult>,
  signal: AbortSignal
) {
  if (modules.length > 3) throw new Error("CONCURRENCY_BUDGET");
  signal.throwIfAborted();
  return Promise.allSettled(modules.map(m => research(m, signal)));
}
// research 内部仍须遵守同一 signal；这里不提供强制终止保证。
// allSettled 保留失败分支，汇总者不能把它们当作已完成。

动手：把判断变成证据

  1. 给三个模块分配互不重叠的范围，定义包含 evidenceIds 与 unresolved 的返回类型。
  2. 对同一组任务比较单 Agent、并行工具、三个子 Agent；先用固定夹具验证调度正确性。
  3. 让一个分支超时，再让父任务取消；检查汇总是否说明缺口，其他分支是否停止。

验收：不会把失败分支包装成完整结论；能说明为何某任务需要独立推理而非普通并发；记录总成本与完成耗时。

完成后再展开：参考解与检查思路

并行工具适合已知独立请求；独立 Agent 适合每个模块都有多轮不确定探索。超时分支在最终结果列为未核实；重试受剩余预算限制。多个分支使用同一证据时应去重并检查版本。

迁移题参考答案
