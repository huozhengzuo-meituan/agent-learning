理解流式输出的事件边界

把流式输出理解为逐步到达的事件，区分已显示文本、完整结果与执行成功。

阅读与检查 15–20 分钟动手任务 25 分钟资料核对 2026-09-22

这一课的具体成果

实现一个只接收明确事件的 UI 状态更新函数，并正确处理半途断流。

前置知识：熟悉 async iteration 或事件监听，完成第 0005 课。

显示了一半，不代表任务成功一半

流式输出让用户在完整回答生成之前看到增量内容。AI SDK 的 streamText提供 textStream，可以逐段读取文本。对前端工程师来说，关键不是“每次多拼一个字符串”，而是清楚区分正在产生内容与一次任务已经完成。

例如先收到“loading 为 true 时”，然后连接中断。界面应保留可见片段并标明未完成，而不能把它记成正常答案。HTTP 响应头成功也不等于后续流一定成功。出错、取消和完成是不同状态，不能都在 finally 里统一设置为“成功”。

传输块不是业务事件

网络把数据分块传输，但一个块可能包含半个事件或多个事件；文本编码也可能跨块。实际使用 SSE、JSON Lines 或 SDK 的流协议时，应由对应解析器恢复事件。ReadableStream 文档介绍了分块读取与消费方式。不要将每次 read() 的原始字节当作一条完整 JSON。

同样，工具参数可能分多次生成。半截参数不能被执行；应用要等完整工具请求形成，再做结构校验与权限判断。流式展示面向用户体验，执行边界面向系统行为。这两条路径可以共享事件来源，但不应共享“看到一点内容就立即执行”的假设。

用明确状态保护界面

本课自定义三个业务事件：文字增量、正常完成和错误。这个小集合不是供应商协议，它是你的服务端完成解析后交给 UI 的事件。真实产品还可能需要工具进度、取消与等待确认；先用小型状态模型，把最容易混淆的完成边界做对。

用户刷新页面、关闭连接或服务端意外结束时，如果没有收到约定的成功信号，就不能擅自推导 complete。部分文本可以保留，但应带着 incomplete 或 failed 的状态，避免后续摘要把半句答案当成已确认事实。

把过程放进 TypeScript

自定义 TypeScript UI 事件片段，不是 AI SDK 原始事件结构。它演示解析后的事件如何更新状态，未连接真实服务。

type StreamEvent =
  | { type: "text"; delta: string }
  | { type: "done" }
  | { type: "error"; message: string };

type ViewState = {
  text: string;
  status: "streaming" | "complete" | "failed";
  error?: string;
};

function reduce(state: ViewState, event: StreamEvent): ViewState {
  if (state.status !== "streaming") return state;
  switch (event.type) {
    case "text":
      return { ...state, text: state.text + event.delta };
    case "done":
      return { ...state, status: "complete" };
    case "error":
      return { ...state, status: "failed", error: event.message };
  }
}

let state: ViewState = { text: "", status: "streaming" };
state = reduce(state, { type: "text", delta: "loading 为 true 时" });
state = reduce(state, { type: "error", message: "连接中断，回答未完成" });

此时 text 被保留，status 是 failed。done 的定义必须由服务端协议说明，不能简单等同于 TCP 连接关闭。代码把终态后的事件忽略，便于暴露事件归属问题；后面会加入 requestId 处理新旧请求并发。

动手：回放三条流

  1. 按顺序回放：text、text、done；text、error；text 后无成功信号便 EOF。
  2. 给第三条轨迹加一段收尾逻辑：仍在 streaming 时转为 failed，并提示输出未完成。
  3. 再测试 done 之后意外收到 text，说明你选择忽略它的理由。
验收条件

只有明确成功事件使状态变成 complete；错误与断流保留部分内容但标明未完成；不对半截 JSON 或工具参数执行业务动作。

做过以后，再看参考答案

第一条应为 complete；第二条为 failed；第三条在流关闭的收尾检查中转 failed。收尾可检查 state.status === 'streaming'，再派发错误事件。终态后追加文本会破坏已提交结果的边界，因此本例忽略它，并在真实系统记录协议异常。

停下来，从记忆里回答

界面收到部分文本后突然断流，应该怎样标记这次回答？

答案与理由

应选“标为尚未完成”。部分文本可供参考，但没有完成信号就不能按成功结果提交。

换个需求，还能用吗？

同事想边生成 JSON 边把每个字段写入正式数据库，你会怎样拆开这两个阶段？

迁移题参考要点

可以把增量对象作为临时预览，但正式写入必须等待完整对象、schema 校验、业务校验与授权条件满足。预览中的字段可能尚未齐全，不能让不完整输出跨过业务提交边界。
