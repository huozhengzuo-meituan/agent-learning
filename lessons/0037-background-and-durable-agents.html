后台 Agent 与持久任务生命周期

设计一个断开浏览器后仍可恢复、取消和审计的后台任务。

阅读 10–15 分钟 · 练习 20–40 分钟来源核对：2026-09-22应用侧 · TypeScript

本课交付：设计一个断开浏览器后仍可恢复、取消和审计的后台任务。

前置：0020 取消、并发与过期结果、0022 检查点、恢复与幂等、0025 用执行轨迹定位问题、0031 长任务的计划与运行支撑

场景统一使用虚构文档与工单。代码注明示意时，需要接入你自己的项目上下文；本页不会发起模型调用。

先理解这个工程问题

后台任务意味着请求连接和任务生命周期分开。用户关闭页面后，运行仍有 runId、持久事件、产物和状态；再次打开可按事件游标续读。把 Promise 放进全局数组，或让服务端持续挂着一个 HTTP 请求，都不能证明进程崩溃后可以恢复。

可采用排队、运行、等待批准、成功、失败、已取消等状态；worker 通过租约领取任务，以版本条件更新状态。事件游标帮助界面去重并续读，业务动作键防止恢复后重复写入。取消是请求与确认两个时刻：远端副作用已经发生时，不能把状态写成取消就假装它未发生。

OpenAI 于 2026-09-10 发布 public beta 的 Agents API，将 Codex harness 和运行基础设施以托管 API 提供；这是特定产品，公测接口与可用性需按当时文档核验。Anthropic 2026-04 的 Managed Agents 工程文章讨论 session、harness 与 sandbox 分离。可借鉴职责划分，但托管不自动代替你的租户授权、业务幂等和验收。

具体失败：worker 写完草稿后崩溃，新 worker 从“运行中”重新执行，产生两份草稿。持久事件应记录动作标识与结果，接手者对账后恢复。下面是纯 TypeScript 状态判断示意，没有冒充任何托管产品 SDK。

读一段代码或执行轨迹

先预测输出或指出边界，再对照注释。以下为课程教学片段；基础机制的可运行实验见 实验说明。本课特定集成需按练习自行实现，未声称已运行。

type Run = {
  id: string;
  status: "queued" | "running" | "waiting_approval" |
    "succeeded" | "failed" | "cancelled";
  version: number;
  cancelRequested: boolean;
};
function mayStartNextAction(run: Run): boolean {
  return run.status === "running" && !run.cancelRequested;
}
const run: Run = {
  id: "r-9", status: "running", version: 7, cancelRequested: true
};
console.log(mayStartNextAction(run)); // false
// 持久层需原子校验 version；取消还要传播到已运行的工具并核对副作用。

动手：把判断变成证据

  1. 画出状态转移图，并标出等待批准恢复、取消确认以及终态禁止再次运行的边界。
  2. 创建六条带序号的虚构事件；模拟客户端从第 3 条断开，再从游标 3 续读并去重。
  3. 模拟 worker 重启：保持同一 runId 与动作键，核对已保存草稿；列一张托管与自托管责任表。

验收：断线重连不丢失或重复显示事件；终态不会被迟到事件改回 running；重启后不重复业务写入。

完成后再展开：参考解与检查思路

客户端仅处理当前 runId 的下一条连续序号：重复事件忽略，出现缺号时先补放事件或重新取得一致快照；终态不得被迟到事件复活。服务端用版本条件阻止过期 worker 覆盖状态。取消请求先阻止新动作，再中断可取消操作并核对已发生效果。托管方可能维护 harness 与执行环境，应用仍拥有身份、资源范围、批准、预算与业务验收。
