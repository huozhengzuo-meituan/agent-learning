把实验变成可运行的服务

为一次 Agent 服务上线定义可回滚的发布单位和可观察的停止条件。

阅读 10–15 分钟 · 练习 20–40 分钟来源核对：2026-09-22应用侧 · TypeScript

本课交付：为一次 Agent 服务上线定义可回滚的发布单位和可观察的停止条件。

前置：0024 评分器、重复试验与回归判断、0025 用执行轨迹定位问题、0026 测量并优化任务成本与延迟、0027 识别提示注入与信任边界、0037 后台 Agent 与持久任务生命周期

场景统一使用虚构文档与工单。代码注明示意时，需要接入你自己的项目上下文；本页不会发起模型调用。

先理解这个工程问题

Agent 的发布单位不只有前端包与服务端镜像。模型配置、提示、工具 schema、Skill、检索索引和评分器也会改变行为。记录这些版本，才能回答“昨天正常，今天错误从哪里开始”。同一代码版本搭配不同模型或知识快照，也可能是另一套系统。

上线先使用虚构数据与离线契约测试，再进入受控试用和小比例灰度。对历史任务做影子评估可以观察回答变化，但影子流量不得执行真实写入。回滚应恢复一组兼容版本；如果新版本已产生外部副作用，回滚程序本身不会撤销它，必须另行对账。

Google SRE 的 canary release 方法提供逐步验证思路。Agent 还要观测证据正确率、批准绕过、任务中断与费用，不能只监控 HTTP 200。SLO应采用业务可理解的口径，例如“在约定预算内完成有依据的只读回答”。

具体失败：新模型更爱调用工具，成功率接近，但每个任务多读十次资料，触发上游限流。灰度需同时限制总并发、每租户预算、工具频率，并有一键停止新任务的开关；停止后保留事件和在途动作状态，便于恢复与追责。

动手：把判断变成证据

  1. 为当前练习项目生成一份发布清单，确保每个字段能够定位具体产物。
  2. 用同一任务集比较基线与候选，预先写明成功率、成本与违规动作的放量条件。
  3. 演练关闭新任务入口、观察在途任务、回滚清单和核对已发生写入四个步骤。

验收：能追溯任一任务所用版本；预设阈值与评估口径；回滚计划区分代码恢复与副作用处理。

完成后再展开：参考解与检查思路

课程可设示例门槛：不允许未经批准的写入，固定评估集证据正确率不降低，预算超限任务不增加。阈值是练习设计，不是行业标准。小样本没有发现违规不代表风险为零，应保留已知限制与持续监控。
