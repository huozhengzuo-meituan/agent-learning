测量并优化任务成本与延迟

用每个成功任务的总成本与端到端延迟，判断一次优化是否值得保留。

阅读 10–15 分钟 · 练习 20–40 分钟来源核对：2026-09-22应用侧 · TypeScript

本课交付：用每个成功任务的总成本与端到端延迟，判断一次优化是否值得保留。

前置：0010 让任务在正确的时候停止、0024 评分器、重复试验与回归判断、0025 用执行轨迹定位问题

场景统一使用虚构文档与工单。代码注明示意时，需要接入你自己的项目上下文；本页不会发起模型调用。

先理解这个工程问题

“首字快了”只说明用户较早看到内容，不能说明任务较早完成。知识助手可能立即输出“正在分析”，随后等待工具十秒。分别记录排队时间、首个有效内容时间、工具时间和完成时间；并发步骤看关键路径，不能把所有子步骤耗时简单相加。

费用也要按任务核算：把失败、重试、缓存写入、缓存读取与工具费用都算进去，再除以成功任务数。下方数据是课程虚构样本，没有使用任何厂商定价。B 方案虽然总费用更低，但成功更少。若质量门槛未达标，就没有资格仅凭便宜胜出。

可以先减少无关上下文、合并重复读取、并行独立只读查询，再尝试模型路由和推理预算。每次只改一项，在同一评估集上比较成功率、延迟分布与费用。依赖前一步文档 ID 的读取不能提前并行；读取一万行再让模型做简单计数，往往可改为工具端过滤。

Claude 的 prompt caching按匹配前缀复用计算，具体寿命、价格和条件以对应模型文档为准。缓存不代表模型记住了用户，也不允许跨用户复用包含私有证据的应用结果。服务目标的定义可参考 Google SRE 的 SLI/SLO 方法。

读一段代码或执行轨迹

先预测输出或指出边界，再对照注释。以下为课程教学片段；基础机制的可运行实验见 实验说明。本课特定集成需按练习自行实现，未声称已运行。

type Batch = { totalCost: number; successes: number; runs: number };
function perSuccess(b: Batch): number | null {
  return b.successes === 0 ? null : b.totalCost / b.successes;
}
const a = { totalCost: 12, successes: 90, runs: 100 };
const b = { totalCost: 10, successes: 60, runs: 100 };
console.log(perSuccess(a)); // 约 0.133，虚构计费单位
console.log(perSuccess(b)); // 约 0.167
// 失败任务仍消耗费用；零成功不能报告为“成本为零”。

动手：把判断变成证据

  1. 建立 10 个虚构任务，记录总耗时、首次有效内容时间、结果和费用；先固定同一个模型配置。
  2. 模拟移除一段不相关文档：保证输入任务和评分器不变，比较成功率与每成功任务成本。
  3. 选一条有依赖链的轨迹，画出可并行部分与关键路径，预测优化能节省的时间。

验收：报告至少包含成功率、总费用、每成功任务成本及完成延迟；零成功批次显示不可定义；不把十个样本称为可靠的生产 p95。

完成后再展开：参考解与检查思路

A 的成功率为 90%，B 为 60%；B 平均每成功任务反而更贵。十个样本只足够练习统计流程，应同时报告原始延迟和样本数，后续用更大样本与重复试验观察尾部延迟。缓存测试要明确冷启动与热缓存比例。

答案：相同评估口径。保持相同任务与评分口径，否则无法判断节约是工程优化还是能力下降。

换个场景再判断

把所有请求都切到小模型，费用下降一半，但需要人工接管的任务翻倍，如何决策？

迁移题参考答案

把人工处理时间和失败影响加入业务成本；再按任务难度分层比较。可以对简单任务路由小模型、困难任务升级，但升级规则也必须评估，不能假设两次调用一定比一次便宜。
