把人工确认做成程序约束

把人工批准绑定到具体动作和参数版本，在执行器中拦截未批准或已改变的写入。

阅读与判断 15–20 分钟实验 20–40 分钟资料核对：2026-09-22

前置：第 0008、0013、0020 课；服务端鉴权与状态机。

能力状态：通用工程机制；本文 TypeScript 是概念示意，未连接真实模型或生产存储。

本课服务于研发知识助手项目；页面备齐不代表已经掌握。以动手结果、解释和后续迁移作为学习证据。

批准一个明确动作，不是批准一段心情

用户看到“要创建任务吗”并点了确认。模型随后把目标项目从 Atlas 改成 Boreal，标题也改了。若服务器只检查 approved=true，用户就批准了自己从未见过的内容。有效批准应绑定动作 ID、完整参数版本、批准者、有效期和作用域。

先由 Agent 生成候选动作，服务器完成参数校验和权限检查，再持久化不可变的审批快照。UI 展示目标、关键字段及影响；用户确认后，执行器使用已批准快照，不能重新向模型询问“最终参数”。参数变化就创建新的待批准版本。

模型可以提议，执行器决定是否放行

下面是服务端内的一段判定逻辑，action 与 approval 都应从服务器数据库读取，actor 应来自已验证的会话。请求方不能自己传一个 approvals 对象让服务器相信。示例用 actionId 与 revision 绑定不可变参数，生产可以补充规范化参数摘要以审计。

type Action = {
  id: string; revision: number; tenantId: string; ownerId: string;
  state: "pending" | "approved" | "consumed";
};
type Approval = {
  actionId: string; revision: number; approverId: string; expiresAt: number;
};
function allowed(a: Action, p: Approval, actor: string, now: number) {
  return a.state === "approved" && a.id === p.actionId &&
    a.revision === p.revision && a.ownerId === actor &&
    p.approverId === actor && p.expiresAt > now;
}
// 调用前先检查租户和工具权限。
// 此布尔检查必须与“认领执行”合在数据库原子操作中，不能先查后改。

简单布尔函数本身挡不住两个 worker 同时读取 approved 后重复执行；第 0022 课会处理执行认领与幂等。暂停和恢复同样要落盘，用户明天再打开仍应看到确切快照。LangGraph 的 interrupt 提供持久暂停与 resume，但节点恢复时会重新执行开始到中断点之前的代码，副作用不能随意放在它前面。资料：Interrupts。

人工确认不是所有工具的默认步骤

本项目可允许授权范围内的只读检索自动执行，创建草稿任务采用一次具体批准。边界由产品政策定义，避免每个 read 都弹窗导致用户机械确认。一个确认也不代表永远授权所有写入。暂停、UI 展示和数据库持久状态需要共同设计，单有对话中的一句“用户已同意”不够。资料：Persistence。

动手：让边界可观察

  1. 建立动作 A/revision=1：在 Atlas 创建“修复缓存”任务，生成确认卡片。
  2. 用户批准后，将动作 revision 改为 2，标题改成“发布版本”；调用判定函数。
  3. 再检查批准过期、另一个用户批准、已 consumed 三种情形。
  4. 在纸上画出两个 worker 同时执行布尔检查的时间线，找出重复写入窗口。

验收：原版本在正确用户和有效期内允许认领；四种变化都拒绝。能解释为什么 allowed=true 不能直接等于“业务写入已完成”。

建议先独立完成；本课代码用于理解机制。实验可在工作区新建笔记或 TypeScript 文件，真实 API 与依赖准备见 实验说明。

完成后查看参考解

审批记录仍是 revision=1，而最新动作是 2，应拒绝并展示新快照。过期、错误批准者与 consumed 同样不满足条件。并发窗口位于“读 approved”和“改 consumed”之间；需要原子认领动作并为外部写入提供稳定幂等键。

UI 只有收到执行成功及结果 ID 后才能显示创建完成；批准成功仅表示可以开始执行。

不看上文，检验一次

用户批准后，目标项目被模型改写，执行器应该怎样处理？

答案与理由（无脚本时也可查看）

答案：要求批准新的版本。批准绑定具体快照。参数变化使原批准不再适用，必须确认新版本。

换个情境，还能做对吗？

批准后用户被移出项目，稍后 worker 才开始执行。旧批准能否绕过当前权限？

迁移题参考思路

不能。批准是用户对动作的意图，不会创造项目访问权限。执行前重新验证当前授权，权限撤销就停止；同时保持审批记录供用户理解为什么任务没有执行。
