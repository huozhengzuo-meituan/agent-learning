MCP 连接了什么，留下了什么

画出 MCP host、client、server 的责任，并保留应用自己的授权与评估。

阅读 10–15 分钟 · 练习 20–40 分钟来源核对：2026-09-22应用侧 · TypeScript

本课交付：画出 MCP host、client、server 的责任，并保留应用自己的授权与评估。

前置：0007 为模型设计清晰的工具契约、0008 实现一个受约束的只读工具、0027 识别提示注入与信任边界、0028 工具权限与执行隔离

场景统一使用虚构文档与工单。代码注明示意时，需要接入你自己的项目上下文；本页不会发起模型调用。

先理解这个工程问题

MCP 把工具、资源和提示等能力的交流方式标准化。你的 Agent 应用是 host；host 为某个 server 管理一个 client；server 暴露专业能力。模型如何选工具、何时停止、谁批准写入、业务成功如何评分，仍需应用负责。连接了一个 MCP server，不等于自动获得一个可靠 Agent。

本课核对的是 2026-07-28 规范架构：请求携带协议版本与能力信息，server/discover 可用于发现能力。旧教程中的连接初始化与状态假设可能属于早期版本，不能直接与这里的消息字段拼接。工程接入要记录协议版本、SDK 版本和对端实际能力。

工具描述帮助模型选择，但工具注解不替代安全策略；返回文本也是外部内容。宿主应把 server 的工具映射成内部契约，执行前验证租户与授权，执行后规范化错误和输出。根据工具规范区分协议错误与工具执行错误，避免把“业务找不到文档”当成网络故障反复重试。

具体失败场景：本地 readDoc 原本检查租户，迁移到 MCP 后开发者只转发参数，误以为远程连接已经鉴权便足够。连接身份只能说明谁在调用，不自动证明他可以访问每个资源。桥接层与资源服务必须继续校验；下方接口仅是课程内部适配器，并非 MCP wire schema。

读一段代码或执行轨迹

先预测输出或指出边界，再对照注释。以下为课程教学片段；基础机制的可运行实验见 实验说明。本课特定集成需按练习自行实现，未声称已运行。

type InternalToolResult =
  | { ok: true; evidenceIds: string[] }
  | { ok: false; code: "DENIED" | "NOT_FOUND" | "UNAVAILABLE" };
type ToolPort = {
  readDoc(input: { tenantId: string; docId: string }): Promise<InternalToolResult>;
};
async function useDoc(port: ToolPort, tenantId: string, docId: string) {
  const result = await port.readDoc({ tenantId, docId });
  if (!result.ok) return { status: result.code };
  return { status: "ready", evidence: result.evidenceIds };
}
// 内部端口的实现可接本地函数或 MCP；授权契约不能随传输替换丢失。

动手：把判断变成证据

  1. 画一张“模型 → host → client → server → 文档存储”的责任图，标出两处权限检查。
  2. 用本地假 server 分别返回工具失败、协议异常和成功的空结果；映射为三个可区分的内部状态。
  3. 记录接入时要核对的协议版本、发现能力、认证方式、资源授权和输出大小限制。

验收：能指出调用协议解决的互通问题和宿主仍承担的三项责任；迁移后越权读取测试继续失败。

完成后再展开：参考解与检查思路

两处检查分别在宿主的工具执行策略与文档服务的数据访问层。NOT_FOUND 是可解释的业务结果，不应无限重试；UNAVAILABLE 可以按预算重试；DENIED 需停止该能力或请求合适授权。协议解码失败单独记录为适配错误。

换个场景再判断

某 server 把 search 的输出从字符串改为结构化内容，如何避免所有调用者一起损坏？

迁移题参考答案

在适配器内做版本与结果校验，保留固定的内部结果类型；用契约测试和少量灰度流量验证新版本，错误时明确失败，不默默把未知对象当成空字符串。
