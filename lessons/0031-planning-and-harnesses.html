长任务的计划与运行支撑

为跨多个上下文的长任务设计可恢复的进度与独立验收证据。

阅读 10–15 分钟 · 练习 20–40 分钟来源核对：2026-09-22应用侧 · TypeScript

本课交付：为跨多个上下文的长任务设计可恢复的进度与独立验收证据。

前置：0012 模型、SDK 与 Harness：现代 Agent 运行时、0022 检查点、恢复与幂等、0024 评分器、重复试验与回归判断、0025 用执行轨迹定位问题

场景统一使用虚构文档与工单。代码注明示意时，需要接入你自己的项目上下文；本页不会发起模型调用。

先理解这个工程问题

长任务的问题不只是提示很长。助手需要汇总十个模块的发布差异，做到一半进程退出；新执行者必须知道已验证的事实、未完成项、产物位置和继续的条件。把这些藏在一段对话中，恢复时容易重复工作或错认完成。

本课的 harness 包含任务规格、受控工具、运行状态、产物、检查与反馈。计划是可修改的导航；验收证据必须对应真实产物版本。OpenAI 2026-02 的工程案例强调把可访问的仓库知识与反馈环境提供给 Agent。该案例的效率结果有特定团队与环境前提，不能当作普遍产能承诺。

每个计划项保持一个小而可验证的交付，例如“模块 A 的三项变更均引用到版本化文档”。状态由执行结果推进，不能因为模型写了“完成”就通过。引用文件修改后，旧验收结果应失效；这和前端构建产物随源码版本变化的道理相同。

Anthropic 2026-03 的长任务实验讨论生成与评估分离，也指出旧模型需要的上下文重置策略可能随模型改善而失去价值。工程支撑应针对观测到的失败建立，并随评估重审，避免把历史补丁永久堆进每次执行。

读一段代码或执行轨迹

先预测输出或指出边界，再对照注释。以下为课程教学片段；基础机制的可运行实验见 实验说明。本课特定集成需按练习自行实现，未声称已运行。

type Item = {
  id: string;
  artifactHash: string;
  state: "todo" | "ready" | "verified";
  checkedHash?: string;
};
function isComplete(item: Item): boolean {
  return item.state === "verified"
    && item.checkedHash === item.artifactHash;
}
const item: Item = {
  id: "module-a", artifactHash: "v2",
  state: "verified", checkedHash: "v1"
};
console.log(isComplete(item)); // false：新产物不能沿用旧验收

动手：把判断变成证据

  1. 把“汇总三个模块发布差异”拆成三个带证据要求的交付项和一个整合项。
  2. 在第二项结束后模拟上下文丢失，只给接手者任务规格、进度记录、产物 ID 和检查结果。
  3. 修改第一项产物的版本，验证完成判断失效；为重新检查写明触发条件。

验收：接手者无需旧聊天就能找到下一项；任何已完成项都有同版本证据；恢复时不会重复生成已验收产物。

完成后再展开：参考解与检查思路

进度记录写目标、约束、完成项与证据、未解问题和下一步；不要复制全部对话。整合项等待三个模块的证据都通过。产物版本发生变化时重跑受影响检查，不能直接把 state 字段改回 verified。
